# TPC-DS expected result sets — DuckDB oracle

Schemas, queries, result checkers, and oracle-generation tools remain public
regression inputs. Performance-driver examples below require the optional local
`scripts-internal/` directory, which is ignored by Git and absent from public
checkouts.

A second, independent reference result set alongside the PostgreSQL one under
`../expected/`. Same idea, different engine: one tab-separated file per query
(`sf-<SF>/qNN.tsv`, no header, `NULL` = literal `NULL`), consumed by
`scripts/tpcds_check_results.py` with the same canonicalization the driver
applies to mydb output (cells trimmed; numbers → integer or 4 dp half-up).

Generated by `scripts/tpcds/duckdb/build_and_run_duckdb.sh <SF>` from the **same**
cached `.dat` files mydb loads (`/tmp/mydb-tpcds-dbgen-cache/sf-<SF>`), running the
**exact** mydb query files (same `dsqgen -rngseed 1 -scale 1` substitution
parameters), transformed only for DuckDB dialect. So these answers correspond to
the SQL mydb runs, just as the PG set does.

```bash
scripts/tpcds/duckdb/build_and_run_duckdb.sh 1      # -> sf-1/
scripts/tpcds/duckdb/build_and_run_duckdb.sh 0.1    # -> sf-0.1/
```

## Why DuckDB in addition to PostgreSQL

DuckDB's `/` is decimal/float division (`5/2 = 2.5`), matching MySQL/mydb;
PostgreSQL's `int / int` truncates (`5/2 = 2`). On the handful of TPC-DS queries
that divide integer columns, the PG oracle therefore diverges from mydb while
DuckDB agrees with it (see the cross-check below). DuckDB is thus the more
faithful oracle for those queries; keeping both lets you tell a real mydb bug
apart from a PG-vs-mydb dialect difference.

## Using it as the checker's expected set

`run_tpcds.sh` auto-picks `expected/sf-<SF>/` (the PG set). To validate against
this DuckDB set instead, point the checker at this dir after a mydb run (mydb
output lands in `/tmp/mydb-tpcds-results/<ts>/qNN_result.txt`):

```bash
python3 scripts/tpcds_check_results.py \
  --expected-dir scripts/tpcds/expected-duckdb/sf-1 \
  --actual-dir   /tmp/mydb-tpcds-results/<ts> \
  --output-csv   /tmp/tpcds_vs_duckdb.csv
```

## How it's generated (`../duckdb/`)

```
duckdb/gen_duckdb_artifacts.py   mydb schema/queries -> DuckDB dialect
duckdb/build_and_run_duckdb.sh   create db -> COPY load .dat -> run 99 queries -> qNN.tsv + REPORT.md
duckdb/schema_duckdb.sql         generated (CREATE DATABASE/USE stripped)
duckdb/queries/qNN.sql           generated (dialect-transformed)
```

DuckDB dialect transforms (semantics-preserving — answers unchanged):

- `group by … with rollup` → `group by rollup(…)` (DuckDB has no MySQL `WITH ROLLUP`).
- `lochierarchy` used *inside* an ORDER BY expression → its
  `grouping(a)+grouping(b)` definition (q36/q70/q86; avoids alias-resolution
  divergence — identical row value).
- `returns` / `at` used as plain identifiers → `"returns"` / `"at"` (DuckDB
  reserves both; an implicit alias like `(subquery) at` is otherwise a parse
  error). `store_returns` etc. are untouched (word boundary).
- `interval N day` and `||` concat are kept verbatim — DuckDB accepts both
  natively (unlike PG, which needs `interval 'N day'`).

Session settings applied to every query so ordering matches mydb:

- `default_null_order = nulls_last_on_asc_first_on_desc` — NULLs sort as the
  largest value (last under ASC, first under DESC), matching `run_tpcds.sh`'s
  default `MYDB_ORDER_BY_NULLS=last` and PG. Lines up the 11 ROLLUP queries with
  NULL-keyed super-aggregate rows.
- `default_collation = NOCASE` — case-insensitive string ordering, matching
  mydb's default `utf8mb4_0900_ai_ci` collation (and PG's locale collation).
  Without it DuckDB's binary codepoint order misplaces e.g. `'NY Metro'` before
  `'North …'`. TPC-DS data is ASCII English, so case is the only axis that
  matters; WHERE filters use exact-case literals that match the data, so row
  selection is unaffected.

DuckDB treats `CHAR(n)` as `VARCHAR` (no blank padding); the checker trims every
cell, so this never shows up in a comparison.

## DuckDB vs the PostgreSQL oracle (cross-validation)

Both oracles were diffed against each other with the checker's canonicalization
(`expected/` vs `expected-duckdb/`). Every difference is an expected cross-engine
*semantic* difference, not a DuckDB error:

| SF | identical | order-only (tie-break) | integer-division (DuckDB matches mydb, PG truncates) |
|----|-----------|------------------------|------------------------------------------------------|
| 0.1 | 97 | q33 | q34 |
| 1   | 92 | q31, q71 | q21, q34, q73, q78, q83 |

- **Order-only**: the `ORDER BY` is not a total order; ties break by each engine's
  scan/join order. Canonicalized + sorted, the two sides are identical.
- **Integer-division**: these queries divide integer columns (e.g.
  `hd_dep_count / hd_vehicle_count`, `inv_before / inv_after`,
  `ss_qty / (ws_qty + cs_qty)`). DuckDB and mydb yield a decimal; PG truncates,
  so it filters/outputs different ratios. **DuckDB is the correct reference for
  mydb here.**
